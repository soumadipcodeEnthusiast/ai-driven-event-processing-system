# Dashboard (REQ-034)

## Decision: Grafana (ADR-0006, partially superseded by ADR-0008)

The REQ-034 observability dashboard ("real-time throughput and error rates")
is a **provisioned Grafana dashboard**, not a custom front-end — see
ADR-0006. The earlier design additionally used Grafana, via the
`yesoreyeram-infinity-datasource` plugin, to show a live `PredictiveAlert`
feed linked to `IncidentPlaybook`s (the `aiops-overview` dashboard). That
part is **removed**: diagnostic-service no longer generates playbooks
(GraphRAG/LLM diagnosis is Appendix C future work, not SRS v1.0 — see
ADR-0008), and `PredictiveAlert` no longer carries a `playbook_id`. Grafana
itself, the Prometheus data source, and the `service-health`/`slo`
dashboards are unaffected.

Everything is config-as-code, generated by `infra/grafana/gen_dashboards.py`:

| Path | Purpose |
|---|---|
| `infra/grafana/provisioning/datasources/datasources.yml` | Prometheus (uid `prometheus`, default) |
| `infra/grafana/provisioning/dashboards/dashboards.yml` | File provider → `/var/lib/grafana/dashboards`, folder **AIOps** |
| `infra/grafana/dashboards/service-health.json` | **The REQ-034 dashboard** — golden signals per service, now also the Grafana home dashboard |
| `infra/grafana/dashboards/slo.json` | SLO compliance and error budgets ([docs/SLO.md](../docs/SLO.md)) |

To regenerate after editing `gen_dashboards.py`:

```bash
python3 infra/grafana/gen_dashboards.py infra/grafana/dashboards
```

## How to open it

```bash
docker compose -f infra/docker-compose.yml up -d
open http://localhost:9030/d/aiops-service-health
```

Anonymous read-only (Viewer) access is enabled for the local stack; admin login is
`admin` / `admin` unless `GRAFANA_ADMIN_PASSWORD` is set. Add auth (or disable anonymous
access) before exposing Grafana outside the internal network.

## Service Health — panels

Refresh: **30 s**.

| Row | Panels |
|---|---|
| Availability | Service up, firing Prometheus alerts |
| Ingestion service (REQ-001 / REQ-004 / REQ-005) | Throughput by outcome, Kafka consumer lag, processing latency p95/p99, actuator HTTP rate/latency, JVM heap |
| Forecasting service / Predictive Analytics (REQ-021 / REQ-025) | Open predictive alerts, forecaster info, forecast runs/latency, alerts by severity |
| Diagnostic service — Anomaly Detection (REQ-016 to REQ-020) | Anomaly score p95 vs. threshold, events scored (kafka/http), anomalies detected, audit-publish failures |
| Archival — Kafka → S3 (REQ-028) | Records archived per topic, S3 upload failures, seconds since the last successful upload |
| Process resources | Resident memory, CPU |

Navigation links at the top lead to **SLOs** and the
[runbooks](../docs/runbooks/README.md).

## Other dashboards

- **AIOps SLOs & Error Budgets** (`/d/aiops-slo`): error budget remaining per SLO, 30-day
  SLI vs. objective, burn rates (1h / 6h / 3d) with page/ticket thresholds, service
  availability, firing burn-rate alerts. There is no diagnosis-availability or
  graph-context-latency SLO any more (see docs/SLO.md §1).

## REQ-034 acceptance criteria

| Criterion | How it is met |
|---|---|
| Dashboard displays real-time throughput and error rates | Service Health dashboard panels query Prometheus directly, refreshing every 30 s. |
| Accessible without authentication on the internal network | Anonymous Viewer access in compose (`GF_AUTH_ANONYMOUS_ENABLED=true`, role Viewer); dashboards are read-only (`editable: false`). |

Reliability of the dashboard itself is monitored: Prometheus scrapes Grafana and
`GrafanaDown` fires after 5 min ([runbook](../docs/runbooks/grafana-down.md)).

## Editing dashboards

Dashboards are generated, not hand-edited: change `infra/grafana/gen_dashboards.py`
and re-run it (see above). Keep the `uid`s stable (`aiops-service-health`,
`aiops-slo`) and reference datasources by uid (`prometheus`). Grafana picks
up changes within 30 s of a container restart or volume refresh.
